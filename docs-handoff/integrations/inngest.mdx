# Inngest

Use [`steel-inngest`](https://www.npmjs.com/package/steel-inngest) to express a
Steel browser session lifecycle as Inngest v4 steps. Successfully checkpointed
steps are memoized when a run resumes, and every session has a finite Steel
timeout as a bounded cleanup backstop.

The package has three runtime exports: `steelMiddleware`,
`withSteelSession`, and `steelScrape`. You bring Playwright, Puppeteer, or
another CDP driver.

## Requirements

- Node.js 20 or later
- `inngest` v4 (`>=4 <5`)
- `steel-sdk` `^0.18.0`

## Install

```bash
npm install steel-inngest steel-sdk inngest
```

Set your Steel API key:

```bash
export STEEL_API_KEY=ste-...
```

## Quickstart

Inject the Steel client as `ctx.steel`, then open, use, and close the Playwright
connection inside one `step.run` callback:

```tsx
import { chromium } from "playwright-core";
import { Inngest } from "inngest";
import { steelMiddleware, withSteelSession } from "steel-inngest";

const inngest = new Inngest({
  id: "price-monitor",
  middleware: [steelMiddleware({ apiKey: process.env.STEEL_API_KEY })],
});

export const checkPrice = inngest.createFunction(
  {
    id: "check-price",
    triggers: { event: "steel/price-monitor.requested" },
  },
  async ({ step, steel, runId }) =>
    withSteelSession(
      step,
      { steel, runId, timeoutMs: 120_000 },
      async (session) =>
        step.run("read-price", async () => {
          const browser = await chromium.connectOverCDP(session.connectUrl);
          try {
            const page = await browser.newPage();
            await page.goto("https://books.toscrape.com/", {
              waitUntil: "domcontentloaded",
            });
            const price = await page
              .locator(".product_pod .price_color")
              .first()
              .textContent();
            return price?.trim() ?? null;
          } finally {
            await browser.close(); // Close the connection, not the Steel session.
          }
        }),
    ),
);
```

The function body is re-executed as Inngest advances its steps. Keeping the CDP
connection inside the browser-work callback prevents a replay from reconnecting
when that step is already memoized. Do not return or log `session.connectUrl`;
it embeds the Steel API key.

The create-step checkpoint does not contain the API key or `connectUrl`. The
wrapper assembles the public handle in memory after verifying that the current
Steel base URL and API key still match a one-way configuration fingerprint
from creation.

## Lifecycle semantics

- **Checkpointed creation is memoized.** Once Inngest records the create step
  result, a replay reuses it.
- **External exactly-once is not guaranteed.** If Steel accepts a create request
  but the step result is not checkpointed, an ambiguous retry can issue the
  request again.
- **Release follows successful work.** A final step releases the session after
  the handler resolves. If the handler throws, its error propagates and the
  release step is not scheduled.
- **Failure cleanup is bounded, not immediate.** A session left by a crashed or
  failed run expires when Steel enforces its finite timeout (five minutes by
  default). The package does not promise that no session can outlive its
  Inngest run.
- **Identity includes the session namespace.** With `runId`, the deterministic
  session UUID is derived from `(runId, stepPrefix)`. Use a distinct
  `stepPrefix` for each session in the same run.
- **Configuration is replay-bound.** Keep the API key and normalized Steel base
  URL stable for the lifetime of a run. Changed configuration fails before
  browser work or release.

## Client configuration

Pass either a pre-built `steel` client or `apiKey`/`baseUrl`, never both. A
supplied client's credentials and base URL are authoritative; conflicting
options are rejected instead of silently mixed.

```tsx
await withSteelSession(step, { apiKey, baseUrl, runId }, handler);
await withSteelSession(step, { steel, runId }, handler);
```

The same rule applies to `steelScrape`: pass either `steel` or
`steelApiKey`/`baseUrl`.

`useProxy` supports the boolean on/off form only. Rich geolocation or
server-proxy configuration is not exposed by this wrapper.
